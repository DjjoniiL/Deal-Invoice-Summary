# Обновление карточки сделки в Marketplace-версии

## Коротко

В текущей Marketplace/serverless-версии приложение пересчитывает суммы счетов по сделке, записывает результаты в пользовательские поля сделки и после записи пытается обновить открытую карточку Bitrix24.

Сам пересчёт сделан аккуратно: приложение не пишет поля каждый раз подряд. Сначала оно сравнивает текущие значения в сделке с рассчитанными значениями и вызывает `crm.deal.update` только если есть реальные отличия.

Спорное поведение находилось не в самом расчёте, а в обновлении интерфейса карточки после записи. До v35 в `PAGE_BACKGROUND_WORKER` при недоступности мягкой команды `reloadData` использовался более жёсткий fallback `BX24.reloadWindow()`.

В v35 этот fallback убран: worker пробует только `reloadData`, а если команда недоступна, сохраняет диагностику и не перезагружает окно Bitrix24.

## Где это находится

Основной Marketplace iframe:

- `marketplace/app.js`
- функция `recalculate(...)`
- функция `refreshDealCard(...)`
- запуск при открытии карточки рядом с логикой `writeOnOpen`

Фоновый worker:

- `marketplace/worker.js`
- функция `recalculateDeal(...)`
- функция `refreshDealCard(...)`
- функция `reloadBitrixWindow(...)`
- мониторинг открытой сделки и CRM-страниц через `checkDeal(...)` и `checkRecentDealChanges(...)`

## Как работает пересчёт при открытии сделки

Когда пользователь открывает карточку сделки, Bitrix24 загружает iframe приложения во вкладке карточки.

Приложение:

1. Получает ID сделки из placement-контекста Bitrix24.
2. Проверяет выбранный режим автопересчёта.
3. Если режим равен `onOpen`, запускает пересчёт с записью результата.
4. Читает сделку через `crm.deal.get`.
5. Читает связанные счета через `crm.item.list` с `entityTypeId=31` и связью `parentId2 = dealId`.
6. Считает суммы: выставлено, оплачено, не оплачено, остаток оплаты.
7. Сравнивает рассчитанные суммы с текущими значениями в пользовательских полях сделки.
8. Если значения отличаются, вызывает `crm.deal.update`.
9. Если значения уже совпадают, запись пропускается.

Важная деталь: пустое поле в сделке не считается равным нулю. Если расчёт дал `0`, а поле в карточке пустое, приложение запишет `0`, чтобы поле было реально заполнено.

## Как обновляется интерфейс в основном iframe

После `crm.deal.update` основной iframe вызывает `refreshDealCard()`.

Эта функция:

1. Проверяет, доступен ли `BX24.placement.call`.
2. Получает список команд placement через `BX24.placement.getInterface`.
3. Ищет команду `reloadData`.
4. Если `reloadData` доступна, вызывает:

```javascript
BX24.placement.call("reloadData", {}, callback)
```

5. Если `reloadData` недоступна, основной iframe не делает полный reload окна. Он только возвращает диагностический результат `reloadData unavailable`.

То есть в основном iframe поведение относительно мягкое: приложение пытается обновить данные карточки через штатный placement-механизм, но не перезагружает весь интерфейс Bitrix24.

## Как работает PAGE_BACKGROUND_WORKER

`PAGE_BACKGROUND_WORKER` - это скрытый iframe приложения, который Bitrix24 может загружать на открытых страницах портала.

Он нужен, чтобы serverless-приложение могло реагировать на уже сохранённые изменения, пока пользователь находится внутри Bitrix24.

Worker:

1. Инициализируется через `BX24.init`.
2. Получает placement-контекст через `BX24.placement.info()` и `PLACEMENT_OPTIONS.URI`.
3. Определяет, находится ли пользователь на странице сделки или в CRM-разделе.
4. Если открыта конкретная карточка сделки, берёт ID из URL.
5. Каждые 5 секунд читает сделку через `crm.deal.get`.
6. Сравнивает короткий снимок сделки: сумма `OPPORTUNITY` и стадия `STAGE_ID`.
7. Если сумма или стадия изменились, пересчитывает связанные счета.
8. Если расчётные поля отличаются, вызывает `crm.deal.update`.
9. После записи пытается обновить карточку.

На страницах CRM без конкретного ID сделки worker смотрит последние изменённые сделки через `crm.deal.list` по `DATE_MODIFY`, держит baseline и пересчитывает только те сделки, у которых изменился snapshot.

## Почему это может мешать пользователю

До v35 worker обновлял карточку более агрессивно, чем основной iframe.

Старая логика в `marketplace/worker.js` была такой:

1. Сначала попробовать `BX24.placement.call("reloadData")`.
2. Если `reloadData` недоступна или вызов завершился ошибкой, попробовать `BX24.reloadWindow()`.

`reloadData` - это мягкий вариант. Он должен обновить данные карточки через placement API.

`BX24.reloadWindow()` - жёсткий вариант. Он может перезагрузить более широкий интерфейс Bitrix24. Из-за этого пользователь может потерять текущий визуальный контекст, открытые панели, фокус ввода или ощущение контроля над карточкой.

Именно это поведение выглядело принудительным: пользователь не нажимал кнопку обновления, но окно Bitrix24 могло обновиться из-за фонового worker.

В v35 полный fallback удалён. Теперь после фоновой записи worker не вызывает `BX24.reloadWindow()`.

## Ограничение serverless-версии

Без backend приложение не может получить полноценные серверные события Bitrix24, пока пользователь офлайн или пока портал не загрузил iframe/worker.

Поэтому текущая serverless-логика держится на трёх сценариях:

1. Пересчёт при открытии карточки сделки.
2. Ручной пересчёт по кнопке.
3. Фоновая проверка через `PAGE_BACKGROUND_WORKER`, пока пользователь находится на страницах Bitrix24.

Worker видит только сохранённые данные, доступные через REST. Несохранённые изменения внутри формы карточки он надёжно поймать не может.

## Более мягкие варианты поведения

### Вариант 1. Убрать полный `BX24.reloadWindow()` из worker - выбран для v35

Worker продолжает пересчитывать и записывать поля, но после записи пробует только `reloadData`.

Если `reloadData` недоступна, worker ничего не перезагружает. Он просто сохраняет диагностику.

Плюсы:

- меньше вмешательства в работу пользователя;
- не перезагружается вся карточка или окно Bitrix24;
- автоматический пересчёт остаётся;
- правка точечная и безопасная.

Минусы:

- иногда пользователь увидит обновлённые поля только после ручного обновления карточки или повторного открытия.

Это выбранный вариант для v35.

### Вариант 2. Worker пишет поля, но вообще не обновляет интерфейс

Фоновый worker только синхронизирует данные в CRM.

После `crm.deal.update` он не вызывает ни `reloadData`, ни `BX24.reloadWindow()`.

Плюсы:

- никакого внезапного влияния на интерфейс пользователя;
- меньше риска сломать рабочий процесс;
- простая модель поведения.

Минусы:

- пользователь может не сразу увидеть новые значения в открытой карточке;
- потребуется объяснить, что поля обновлены в CRM, но карточка может показать их после обновления.

### Вариант 3. Обновлять карточку только после действия пользователя

Автоматический worker может записывать поля без refresh, а ручной пересчёт по кнопке во вкладке приложения может делать `reloadData`.

Логика такая:

- пользователь нажал кнопку пересчёта - можно обновить карточку;
- worker пересчитал сам - интерфейс не трогаем.

Плюсы:

- понятная граница: явное действие пользователя может менять интерфейс;
- фоновые процессы не вмешиваются;
- ручной сценарий остаётся удобным.

Минусы:

- при автоматическом пересчёте открытая карточка не всегда визуально обновится сразу.

### Вариант 4. Сделать настройку обновления карточки

Добавить настройку вроде:

```text
Обновлять карточку после автоматического пересчёта
```

По умолчанию её лучше выключить.

Плюсы:

- администратор сам выбирает поведение;
- можно оставить старое поведение для тех, кому оно нужно.

Минусы:

- новая настройка усложняет интерфейс;
- потребуется аккуратно менять UI, документацию и тесты;
- так как дизайн главного экрана утверждён, такую правку лучше делать отдельно и осознанно.

### Вариант 5. Показывать результат только в диагностике приложения

Worker после записи сохраняет статус в `localStorage` или `app.option`, а приложение при открытии показывает, что поля были обновлены.

Плюсы:

- без принудительного обновления карточки;
- есть следы работы автоматики;
- удобно для диагностики.

Минусы:

- это не мгновенное визуальное обновление карточки;
- пользователю нужно открыть приложение или журнал, чтобы увидеть подробности.

## Рекомендация

Для v35 выбран следующий шаг: убрать fallback `BX24.reloadWindow()` из `marketplace/worker.js`.

Оставить можно так:

- основной iframe: пробует `reloadData` после ручного пересчёта или пересчёта при открытии;
- worker: записывает поля, пробует только `reloadData`, а если команда недоступна - не делает полный reload;
- `BX24.reloadWindow()` не использовать для фонового автоматического сценария.

Так приложение сохранит автоматический пересчёт, но перестанет принудительно перезагружать рабочую карточку Bitrix24.

## Что важно не делать

Для текущей Marketplace/serverless-версии не стоит:

- добавлять внешний backend только ради обновления карточки;
- подключать Beget или VibeCode для режимов `Постоянный` и `Утром и вечером`;
- добавлять OAuth-секреты или API-ключи в Marketplace zip;
- делать скрытую полную перезагрузку окна Bitrix24 без явного действия пользователя;
- править финальный дизайн главного экрана без отдельного подтверждения.

# План адаптации для Bitrix24 Marketplace

## Цель

Подготовить отдельный zip-архив статического приложения для загрузки в Bitrix24 Marketplace без собственной серверной части. Документация, тесты, исходная серверная версия и служебные файлы остаются в репозитории, но не попадают в Marketplace zip.

## Текущий статус

На 2026-08-12 serverless-адаптация подготовлена в папке `marketplace/` и проверяется на тестовом портале `https://vibecod1.bitrix24.ru`. Последний локальный архив для загрузки: `Калькулятор счетов Marketplace v15-6.zip` (`layout-20260812-5`).

Что уже перенесено в Marketplace-версию:

- финальный дизайн основного экрана из серверной версии;
- пункт левого меню через `LEFT_MENU`;
- создание стандартных пользовательских полей сделки;
- отображение человекочитаемых названий полей вместо символьных кодов;
- сохранение сопоставления через `app.option.*`;
- попытка автоматического добавления раздела `Расчёт оплаты счетов` в карточку сделки при `Создать автоматически` и `Сохранить сопоставление`;
- настройка раздела карточки сделки по доступным воронкам через `crm.category.list` и `extras.dealCategoryId`, потому что в Bitrix24 раскладки карточек сделок зависят от воронки;
- fallback для ответа `Card layout is empty`: Marketplace-версия создаёт безопасную дефолтную раскладку и добавляет в неё раздел `Расчёт оплаты счетов`;
- ручной пересчёт по ID или ссылке сделки;
- человекочитаемые названия стадий счетов через `crm.status.list` по `SMART_INVOICE_STAGE_*` и `DYNAMIC_31_STAGE_*` для новых счетов Bitrix24; если `crm.status.list` возвращает полный `STATUS_ID` вида `DT31_2:S`, приложение использует его приоритетно вместо числового `ID` строки, если возвращает короткий `STATUS_ID`, собирает полный ключ из `ENTITY_ID`/`STATUS_ID` или из префикса запроса, а также диагностирует справочник через `crm.status.entity.types`;
- ФИО ответственных в таблице счетов через `user.get` и нормализацию ID пользователей;
- даты выставления и сроки оплаты в таблице и CSV-отчёте в формате `ДД.ММ.ГГГГ` без времени;
- накопительный установочный журнал с timestamp и 4-секундной паузой перед завершением установки;
- ручной массовый пересчёт всех сделок со счетами в выбранном окне 42/28/21/14/7/2 суток с прогрессом и формированием CSV-отчёта за период;
- окно заявки на серверную версию при выборе режимов `Утром и вечером` или `Постоянный`; окно не показывается, если портал уже имеет серверный флаг в `app.option`;
- режим `При открытии сделки` выбран по умолчанию; ручной пересчёт по кнопке и массовый пересчёт доступны без серверного окна;
- поле `Расписание` в блоке `Автопересчёт`: `по кнопке` для ручного режима, `в 9:45 утра И в 18:45 вечера` для режима утром/вечером, `Каждый час с 09:00 до 20:00` для постоянного режима;
- автоматический возврат режима на `При открытии сделки` при закрытии окна заказа серверной версии без серверного флага;
- справочный расход micro-сервера в окне серверных режимов за 30 рабочих дней: до `200 руб/мес` для `Постоянный` и до `145 руб/мес` для `Утром и вечером`;
- CSV-отчёт в браузере по кнопке `Скачать отчёт` после формирования;
- cache-busting ассетов `layout-20260812-5`, расширенный журнал ошибок и статический `PAGE_BACKGROUND_WORKER`;
- режим `При открытии сделки`, который при загрузке вкладки карточки пересчитывает связанные счета и обновляет расчётные поля только если значения изменились;
- повторный пересчёт в открытой карточке при изменении суммы или стадии сделки;
- заголовок над таблицей с ID сделки, ссылкой на сделку и закреплённой суммой из карточки;
- порядок колонок счетов: `Счёт`, `Срок оплаты`, `Ответственный`, `Сумма`, `Стадия`, `Дата выставления`;
- поле остатка с названием `Остаток оплаты сделки`;
- режим `При изменении сделки/счёта`, который в Marketplace работает через `PAGE_BACKGROUND_WORKER` на открытых страницах портала.

- `layout-20260812-3`: монитор открытой карточки работает по сохранённым данным Bitrix24: polling не блокируется скрытым iframe, дополнительно запускается при `focus`, `pageshow`, `visibilitychange` и пробует подписаться на события, если они объявлены через `BX24.placement.getInterface`. Несохранённые правки в форме карточки без backend/документированного события остаются вне надёжного serverless-сценария.
- `layout-20260812-4`: добавлен статический `PAGE_BACKGROUND_WORKER` для открытых страниц портала. Worker берёт текущий URL из `BX24.placement.info()`/`PLACEMENT_OPTIONS.URI`, активируется на карточках сделок, проверяет сохранённые `OPPORTUNITY` и `STAGE_ID` раз в 5 секунд, пересчитывает поля через прямой Bitrix24 REST и после записи пробует обновить карточку через `reloadData` или `BX24.reloadWindow`. Режим `При изменении сделки/счёта` больше не требует внешней обработки в Marketplace-сценарии открытой страницы.
- `layout-20260812-5`: worker безопасно разбирает настройки `dealInvoiceSummarySettings` и возвращается к значениям по умолчанию, если Bitrix24 или `localStorage` вернули нестандартный/повреждённый формат.
## Состав Marketplace zip

- `install.html` — обязательный установщик приложения.
- `install.js` — логика установки: накопительный журнал, `placement.bind` для `LEFT_MENU` и `PAGE_BACKGROUND_WORKER`, затем `BX24.installFinish()`.
- `install.css` — стили установщика.
- `index.html` — основной экран приложения и вкладка сделки.
- `app.js` — расчёт, создание полей, сохранение настроек и вызовы REST через `BX24.callMethod`.
- `style.css` — стили приложения.
- `worker.html`, `worker.js`, `worker-error.html` — статический фоновый worker Bitrix24 для мониторинга сохранённых изменений открытой карточки сделки.

## Перенос логики

1. Заменить серверные VibeCode API-вызовы на прямые Bitrix24 REST-вызовы из iframe:
   - `crm.deal.get`;
   - `crm.deal.update`;
   - `crm.deal.fields`;
   - `crm.deal.userfield.list`;
   - `crm.deal.userfield.add`;
   - `crm.item.list` с `entityTypeId=31`;
   - `crm.status.list` для справочника стадий новых счетов `SMART_INVOICE_STAGE_*`;
   - `user.get` для ФИО ответственных.
2. Хранить настройки маппинга через `app.option.*`, с fallback в `localStorage` для dev-установки.
3. Считать суммы только по текущему списку счетов, полученному из Bitrix24; удалённые счета не учитываются, потому что `crm.item.list` их не возвращает.
4. Оставить CSV-экспорт в браузере через `Blob`.

## Ограничения serverless-версии

Статический zip без сервера не может принимать входящие HTTP-события Bitrix24 как внешний обработчик. Для сценария уже открытой страницы используется официальный `PAGE_BACKGROUND_WORKER`: это не внешний backend, а скрытый iframe приложения, который Bitrix24 загружает на страницах портала. Он реагирует только пока у пользователя открыта страница портала и видит только сохранённые данные, доступные через REST.

## План serverless-доработки

Текущий Marketplace-этап реализовал режим `При открытии сделки`. Это почти автоматический режим без сервера: пользователь открывает карточку сделки, Bitrix24 загружает iframe приложения, `marketplace/app.js` получает ID сделки из `PLACEMENT_OPTIONS`, читает сделку и связанные счета через `BX24.callMethod`, считает суммы и обновляет поля сделки через `crm.deal.update`, если значения изменились.

Рабочие пункты:

1. Добавить режим `При открытии сделки` в список автопересчёта. Реализовано в `layout-20260812-1`.
2. При загрузке вкладки сделки запускать пересчёт с записью результата. Реализовано в `layout-20260812-1`.
3. Перед записью сравнивать текущие и рассчитанные значения, чтобы не обновлять сделку без необходимости. Реализовано в `layout-20260812-1`.
4. Убрать пункт `Ручной` из списка режимов, но оставить ручной пересчёт и массовый пересчёт по окну только по кнопке. Реализовано в `layout-20260812-2`.
5. В открытой карточке повторять пересчёт при изменении суммы или стадии сделки. Усилено через `PAGE_BACKGROUND_WORKER` в `layout-20260812-4`.
6. Режим `При изменении сделки/счёта` в Marketplace работает через `PAGE_BACKGROUND_WORKER` на открытых страницах портала.
7. Режимы `Утром и вечером` и `Постоянный` не запускать в serverless-версии и не подключать к Beget.

## Проверка перед упаковкой

1. `npm run lint`
2. `npm test`
3. Собрать новый Marketplace zip только из файлов папки `marketplace/`; для каждого крупного изменения использовать новое имя с номером версии или commit short SHA. Не обновлять старый безымянный zip и не собирать архив с серверной версией.
4. Установить архив на тестовом портале через developer console.
5. В developer console для версии приложения включить добавление основной страницы приложения в левое меню и указать название пункта меню `Расчёт оплаты счетов`. Это делается настройкой версии/описания приложения, а не `placement.bind`, чтобы Bitrix24 открывал приложение как основной iframe/слайдер.
6. Проверить, что `LEFT_MENU` появился после установки. Вкладку сделки настроить в developer console. Не вызывать `placement.bind` для `CRM_DEAL_DETAIL_TAB` из `install.js`: install token Marketplace-архива может не иметь нужных прав.
7. Проверить внешний вид: Marketplace-версия должна повторять утверждённый основной экран серверной версии, а не использовать отдельный упрощённый шаблон.
8. Проверить создание полей, сопоставление, вкладку сделки и ручной пересчёт.

## Граница Marketplace-only

Текущая задача решается только в статическом Marketplace zip без внешнего backend. Для реакции на сохранённые изменения открытой сделки используется `PAGE_BACKGROUND_WORKER`; для ручных сценариев остаются кнопка пересчёта одной сделки и массовый пересчёт по окну через Bitrix24 JS SDK/REST.

В рамках Marketplace-пакета не добавлять внешние обработчики, OAuth-секреты, API-ключи, Beget/VibeCode вызовы или архивы серверной версии. Любые дальнейшие эксперименты по сумме сделки сначала должны проверять официальные возможности Bitrix24, доступные из zip: placements, `BX24.placement.*`, `BX24.reloadWindow` и прямые REST-методы из iframe.

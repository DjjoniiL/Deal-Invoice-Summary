# Deal Invoice Summary

Первая MVP-версия приложения для Bitrix24/VibeCode. Приложение добавляет во вкладку карточки сделки отчёт `Расчёт оплаты счетов`: считает суммы счетов, привязанных к сделке, показывает структуру оплаты и при необходимости записывает итоги в пользовательские поля сделки.

## Права Bitrix24 для Marketplace

Текущая Marketplace/serverless-версия `Deal Invoice Summary v.36 Marketplace B24` проверена на портале с минимальным набором прав:

- `CRM / crm` - чтение сделок и связанных счетов, массовый пересчёт, запись рассчитанных значений в поля сделки, создание/обновление пользовательских полей сделки, чтение стадий, воронок и настройка блока в карточке сделки.
- `Встраивание приложений / placement` - регистрация CRM-вкладки и `PAGE_BACKGROUND_WORKER`, удаление старых привязок, получение placement-контекста и мягкое обновление карточки через `reloadData`.
- `Пользователи (минимальный) / user_brief` - только `user.get` для отображения ФИО ответственного за счет.

Отдельный скоуп `Базовый / basic` в списке прав Marketplace не выбирается и для модерации не указывается. Проверка 2026-08-31 показала, что приложение корректно устанавливается и работает у администратора и сотрудника без административных прав с выбранными правами `CRM`, `Встраивание приложений` и `Пользователи (минимальный)`. Методы `app.option.get`, `app.option.set` и `user.admin` используются приложением, но отдельного selectable scope в заявке Marketplace для них нет.

Пользовательский скоуп должен быть именно `Пользователи (минимальный) / user_brief`, а не `Пользователи (базовый) / user_basic` и не полный `Пользователи / user`.

`user_brief` нужен только для метода `user.get`: приложение получает ID ответственного за счёт и показывает ФИО в таблице счетов и CSV-отчёте. Контактные данные сотрудников, e-mail, телефоны, логины и пользовательские поля профиля сотрудника приложению не требуются. Приложение не создаёт пользователей, не изменяет профили пользователей и не использует `user.add`, `user.update` или `user.userfield.*`.

`Пользовательские поля пользователя / user.userfield` не запрашивать: приложение использует только пользовательские поля сделок CRM через `crm.deal.userfield.*`, которые относятся к скоупу `CRM / crm`.

## Итоговая Marketplace v34

v34 считается финальной стабильной базой для публикации и ручной загрузки в Bitrix24 Marketplace. Новые изменения после неё делать только через следующую номерную версию, с обновлением `appVersion`, `runtime/cache marker`, документации, тестов и нового versioned zip.

Что важно в финальной сборке:

- installer не создаёт новый `LEFT_MENU` через `placement.bind`, а только очищает старые runtime-привязки и регистрирует `PAGE_BACKGROUND_WORKER`;
- основной пункт левого меню задаётся настройкой версии Marketplace;

### Как победили автозапуск чата

Виджет открытой линии Bitrix24 загружается асинхронно и не всегда даёт один стабильный публичный API. Рабочее решение находится в `marketplace/settings.js`: страница настроек открывается с `?openChat=1`, пробует известные API (`B24Chat`, `BX.SiteButton`, `Bitrix24WidgetObject`), затем DOM fallback по кнопкам виджета. После первого успешного API-вызова, клика по видимой кнопке или появления признаков раскрытого виджета выставляется `chatOpenDetected`, очищается таймер и отключается `MutationObserver`. Это убрало проблему многократного открытия чата после усиления retry-логики.

Практика на будущее: для стороннего виджета с асинхронной загрузкой retry нужен, но обязательно нужен stop condition. Надёжные стоп-сигналы: успешный API-вызов, клик по видимому target, появление iframe/контейнера открытого чата, `MutationObserver` для поздней отрисовки.

### Диаграмма и список сделок

Статистика периода строится в `marketplace/app.js` по группам сделок: завершённые, ожидающие доплаты, без счетов. Для каждого сектора сохраняются `dealIds`, `stageIds` и semantic-группа. При клике приложение открывает стандартный список сделок Bitrix24 с гарантированным фильтром `FILTER[ID]` по ID группы и дополнительными фильтрами `FILTER[STAGE_SEMANTIC_ID]`/`FILTER[STAGE_ID]`.

Практика на будущее: в стандартных Bitrix24 URL-фильтрах главным гарантированным фильтром считать список ID. UI-поле вроде `Группа стадий` может визуально не заполниться даже при передаче semantic/stage параметров, поэтому критичные переходы из диаграмм должны всегда передавать точный набор CRM entity ID.

## Функциональность MVP

- Вкладка `Расчёт оплаты счетов` в карточке сделки Bitrix24.
- Автоматическое определение ID сделки из query-параметров и placement options.
- Получение сделки и связанных счетов через VibeCode REST proxy.
- Расчёт:
  - выставлено по счетам;
  - оплачено;
  - не оплачено;
  - остаток оплаты по сумме сделки;
  - всего счетов;
  - счетов в расчёте;
  - пропущенных счетов в отрицательных стадиях.
- Исключение отрицательных стадий счетов из расчёта по умолчанию.
- Кнопка пересчёта, которая записывает итоги в поля сделки.
- Кликабельные счета в таблице: карточка счета открывается во внутреннем окне Bitrix24 через `BX24.openPath`.
- Таблица счетов показывает номер, срок оплаты, ответственного, сумму, стадию и дату выставления.

## Автопересчёт

### Marketplace serverless: пересчёт при открытии сделки

Для Marketplace/serverless-версии главный автоматический сценарий без сервера — пересчёт при открытии карточки сделки. Это правильный и ожидаемый режим для статического Marketplace-приложения: оно работает, когда пользователь открыл карточку или основной экран приложения, и не требует отдельного backend.

Как это работает:

- пользователь открывает карточку сделки;
- в карточке загружается iframe приложения во вкладке/placement;
- `marketplace/app.js` получает ID сделки из `PLACEMENT_OPTIONS`;
- приложение обращается к Bitrix24 через `BX24.callMethod`;
- читает сделку через `crm.deal.get`;
- читает связанные счета через `crm.item.list` с `entityTypeId=31` и `parentId2 = dealId`;
- считает суммы выставленных, оплаченных, неоплаченных счетов и остаток;
- при включённом режиме `При открытии сделки` может сразу записать результат в поля сделки через `crm.deal.update`;
- пока карточка сделки открыта, приложение мягко проверяет изменение суммы и стадии сделки и при изменении повторяет пересчёт.

Чтобы не менять карточку без необходимости, до записи нужно сравнивать текущие значения расчётных полей с новым результатом. Если значения уже совпадают, приложение ничего не записывает. Ручной пересчёт по кнопке и массовый пересчёт по окну остаются доступными внутри Marketplace и работают через Bitrix24 JS SDK/REST без сервера.

План serverless-доработки Marketplace:

1. Добавить в список режимов пункт `При открытии сделки`. Реализовано в `layout-20260812-1`.
2. При открытии карточки сделки автоматически считать связанные счета и обновлять поля, если значения изменились. Реализовано в `layout-20260812-1`.
3. Убрать пункт `Ручной` из списка режимов автопересчёта и сделать `При открытии сделки` режимом по умолчанию. Реализовано в `layout-20260812-2`.
4. Пока карточка сделки открыта, повторять пересчёт при изменении суммы или стадии самой сделки. Усилено через `PAGE_BACKGROUND_WORKER` в `layout-20260812-4`.
5. Ручной пересчёт по кнопке и массовый пересчёт по выбранному окну оставить доступными без фонового запуска.
6. Режим `При изменении сделки/счёта` в Marketplace работает через `PAGE_BACKGROUND_WORKER` на открытых страницах портала.
7. Режимы `Утром и вечером` и `Постоянный` не подключать к Beget и не запускать в текущем Marketplace zip.

Текущий Marketplace-пакет не принимает входящие HTTP-события и не требует внешнего backend. Для открытых страниц портала используется официальный `PAGE_BACKGROUND_WORKER`: Bitrix24 загружает скрытый iframe приложения, worker читает сохранённые значения сделки через REST, при изменении `OPPORTUNITY` или `STAGE_ID` пересчитывает поля и пробует обновить карточку только через мягкий `reloadData`. Если `reloadData` недоступен, полный `BX24.reloadWindow()` не вызывается.

## Принцип расчёта

Счета выбираются по `parentId2 = dealId`. Сумма счета берётся из `opportunity`.

Стадии классифицируются так:

- оплаченные: семантика `S`/`SUCCESS` или stage suffix `P`;
- отрицательные: семантика `F`/`FAILURE` или stage suffix `D`;
- остальные считаются неоплаченными.

По умолчанию отрицательные стадии пропускаются. Если включить `includeNegativeStages`, отрицательные счета попадут в неоплаченные.

Остаток считается как:

```text
remaining = dealAmount - paid
```

## Git и публикация

Push в GitHub выполняется только после загрузки локальных правок на портал и ручной проверки пользователем. Даже если lint, тесты и commit уже готовы, до отдельного подтверждения пользователя после проверки на портале push не делать.

Локальные коммиты по обычному рабочему ритму делать после каждого третьего существенного изменения, чтобы история не дробилась слишком мелко. Если пользователь в конкретной сессии явно требует commit в обязательном цикле изменений, выполнить commit в конце этого цикла.

После каждого крупного изменения Marketplace-версии обязательно собирать новый локальный архив только для безсерверного Marketplace-пакета с пометкой номера версии или commit short SHA в имени. Серверные архивы больше не создавать. Безымянный `Калькулятор счетов Marketplace.zip` не обновлять; для проверки и загрузки на портал использовать только новые versioned zip-архивы.

## Marketplace v35

v35 создана как точечная правка поверх v34: фоновый worker больше не делает полный `BX24.reloadWindow()` после автоматического пересчёта. Это сохраняет запись актуальных расчётных полей, но убирает принудительную перезагрузку окна Bitrix24, которая могла мешать работе пользователя в карточке сделки.

## Marketplace v36

v36 добавляет мягкое обновление после возврата к канбану без сервера и без полной перезагрузки окна Bitrix24. `PAGE_BACKGROUND_WORKER` теперь запоминает последнюю увиденную карточку сделки в `dealInvoiceSummaryLastSeenDeal`, на каждом цикле заново читает контекст через `BX24.placement.info()`/`PLACEMENT_OPTIONS.URI`, распознаёт kanban URL и раз в 15 секунд приоритетно проверяет последнюю сделку через `crm.deal.get`.

Если пользователь открыл сделку с канбан-доски, сохранил изменения и вернулся на канбан, worker пытается пересчитать именно эту сделку операцией `background-kanban-return-recalculate`. Если точный ID последней сделки недоступен, остаётся общий безопасный механизм `crm.deal.list` по `DATE_MODIFY DESC`, который обрабатывает последние изменённые сделки. Полный `BX24.reloadWindow()` по-прежнему не используется.

При будущей ручной проверке использовать v34 как baseline:

## Marketplace static

Папка `marketplace/` содержит отдельную serverless-адаптацию для загрузки в Bitrix24 Marketplace как статический zip-архив:

- `install.html`, `install.js`, `install.css` — установщик, очистка старых runtime-привязок левого меню, регистрация `PAGE_BACKGROUND_WORKER` и `BX24.installFinish()`;
- `index.html`, `app.js`, `style.css` — интерфейс приложения, расчёт через `BX24.callMethod` без VibeCode backend.
- `worker.html`, `worker.js`, `worker-error.html` — статический фоновый worker Bitrix24 для открытых страниц портала.

Установщик очищает старые runtime-привязки `LEFT_MENU`, регистрирует `PAGE_BACKGROUND_WORKER` через `placement.bind`, затем завершает установку через `BX24.installFinish()`. Основной пункт левого меню и вкладка карточки сделки для Marketplace-приложения настраиваются в developer console в карточке приложения/версии: основной пункт должен вести на `index.html`, CRM deal placement тоже должен вести на `index.html`. Это важно, потому что дополнительный `placement.bind` для `LEFT_MENU` поверх настройки версии даёт дубли, а install token Marketplace-архива может не иметь прав на `CRM_DEAL_DETAIL_TAB` и возвращать ошибку `The request requires higher privileges than provided by the access token`.

Эта версия не содержит серверной части и не может принимать POST-события Bitrix24. Для неё доступны установка, создание полей, сопоставление, ручной расчёт, массовый расчёт по окну, запись итогов, CSV-отчёт и реакция на сохранённые изменения открытой сделки через `PAGE_BACKGROUND_WORKER`.

Текущий serverless-режим Marketplace `При открытии сделки`: при загрузке вкладки сделки приложение получает ID сделки из `PLACEMENT_OPTIONS`, пересчитывает связанные счета через Bitrix24 REST и обновляет поля сделки только при отличии значений. Режим `При изменении сделки/счёта` использует `PAGE_BACKGROUND_WORKER`: пока пользователь находится на страницах портала, worker определяет открытую карточку сделки по URL или отслеживает свежие сделки на CRM-страницах/канбане через `crm.deal.list` по `DATE_MODIFY`, проверяет сохранённые сумму и стадию и запускает тот же пересчёт без внешнего backend.

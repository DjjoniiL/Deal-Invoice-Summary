# Спецификация проекта

## Название

Deal Invoice Summary / Расчёт оплаты счетов

## Назначение

Приложение для Bitrix24, которое показывает в карточке сделки финансовую сводку по связанным счетам: сколько выставлено, оплачено, не оплачено и какой остаток по сделке. MVP предназначен для тестового портала VibeCode и дальнейшей подготовки к публикации в Marketplace.

## Целевая среда

- Портал: `https://vibecode01.bitrix24.ru`
- VibeCode server ID: `c576798a-ec5f-4491-b6a2-b28e74fc445f`
- Production URL: `https://app-2657fd62db74.vibecode.bitrix24.tech`
- Runtime: `node20`
- Internal port: `3000`
- Access mode сервера: Black Hole

## Основные сценарии

1. Пользователь открывает приложение из левого меню Bitrix24.
2. Пользователь настраивает сопоставление расчётных полей сделки или создаёт стандартные поля автоматически.
3. Пользователь проверяет расчёт вручную по ID сделки или ссылке на сделку.
4. Backend загружает сделку и связанные счета через VibeCode REST proxy.
5. Backend считает итоговые суммы и возвращает JSON.
6. Приложение записывает итоговые суммы в сопоставленные поля сделки.
7. Совместимый маршрут `/deal-tab` продолжает отображать отчёт в формате вкладки сделки.
8. Пользователь может скачать отчёт в формате CSV, открываемом Excel.
9. Пользователь может открыть карточку счёта из таблицы во внутреннем окне Bitrix24.

## Бизнес-логика

Счета связаны со сделкой через `parentId2 = dealId`.

Сумма счета берётся из `opportunity`. Если значение отсутствует, расчётная функция также умеет принять `amount` или `PRICE`.

Стадии счетов классифицируются по семантике:

- `S` или `SUCCESS` — оплаченный счёт;
- `F` или `FAILURE` — отрицательная стадия;
- suffix `P` — оплаченный счёт;
- suffix `D` — отрицательная стадия;
- остальные стадии — неоплаченный счёт.

По умолчанию отрицательные стадии исключаются из сумм. Их количество попадает в `skippedNegative`. Если настройка `includeNegativeStages` включена, такие счета считаются неоплаченными.

Формулы:

```text
issued = сумма всех учитываемых счетов
paid = сумма оплаченных учитываемых счетов
unpaid = сумма неоплаченных учитываемых счетов
remaining = сумма сделки - paid
```

## Пользовательские поля

Стандартный маппинг:

- `ufCrmInvSumIssued` — выставлено;
- `ufCrmInvSumPaid` — оплачено;
- `ufCrmInvSumUnpaid` — не оплачено;
- `ufCrmInvSumRemaining` — остаток по сделке.

Настройки хранятся в `data/settings.json`.

## API приложения

- `GET /api/health`
  - Возвращает `{ "ok": true }`.
- `GET /api/bootstrap`
  - Возвращает настройки, поля сделки, портал и режим доступа.
- `POST /api/settings`
  - Сохраняет настройки маппинга.
- `POST /api/fields/ensure`
  - Создаёт стандартные поля сделки, если их ещё нет.
- `GET /api/deal-summary?dealId=ID`
  - Возвращает расчёт без записи в сделку.
- `POST /api/recalculate/deal`
  - Принимает `{ "dealId": number }`, считает и записывает итоги в сделку.
- `GET /api/deal-report?dealId=ID`
  - Возвращает CSV-отчёт с BOM и `Content-Disposition: attachment`.
- `POST /api/recalculate/recent`
  - Пересчитывает сделки, у которых счета созданы за выбранное окно автопересчёта, по умолчанию 21 сутки.
- `GET /api/automation/status`
  - Возвращает состояние polling-автопересчёта, интервал, окно свежих счетов, последний запуск и watchlist.
- `POST /api/automation/run`
  - Запускает polling-автопересчёт немедленно.

## Frontend

Основной экран левого меню:

- компактный заголовок с порталом и режимом доступа;
- блок обращения за доработкой приложения;
- сопоставление расчётных полей сделки;
- кнопка создания стандартных полей;
- блок состояния автопересчёта;
- ручная проверка по ID сделки или ссылке на сделку;
- скрытый по умолчанию журнал логирования.
- статус polling-автопересчёта и ручной запуск автопрохода.
- режим расчёта в блоке автопересчёта: `Утром и вечером` сейчас использует polling fallback, `Постоянный` зарезервирован для будущих push-событий;
- выбор окна пересчёта в блоке автопересчёта и компактная шкала статуса ручного автопрохода.

Маршрут `/deal-tab` сохранён как совместимый экран отчёта:

- верхний компактный заголовок;
- увеличенный круговой график покрытия оплаты;
- четыре числовые карточки;
- блок `Структура счетов` под числовыми карточками;
- таблица счетов;
- контрастная кнопка скачивания отчёта.

Вкладка использует Bitrix24 JS SDK:

```javascript
BX24.openPath('/crm/type/31/details/{invoiceId}/')
```

Если SDK недоступен, используется fallback `window.open`.

## Backend

Backend реализован на нативном HTTP-сервере Node.js без Express и без внешних зависимостей. Это снижает потребление памяти и ускоряет cold start на маленьком сервере.

Ключевые файлы:

- `src/server.js` — HTTP API, static serving, отчёты, интеграция с расчётом.
- `src/vibeClient.js` — клиент VibeCode REST.
- `src/summary.js` — чистая расчётная логика.
- `public/styles.css` — общие стили и экран отчёта.
- `public/menu.css` — финальный компактный дизайн экрана левого меню.
- `DESIGN_GUIDE.md` — утверждённое описание финального дизайна и запрет на изменение визуальной части без отдельного подтверждения.

Фоновый автопересчёт текущей версии реализован как polling fallback, потому что сервер создан под личным `vibe_api_...`, а VibeCode push `event-subscriptions` требуют сервер под OAuth app key `vibe_app_...`. Polling хранит отслеживаемые сделки в `data/watchlist.json`, добавляет сделку в watchlist после ручного пересчёта и пересчитывает watchlist плюс сделки со счетами, созданными за выбранное окно. По умолчанию окно 21 сутки, доступны варианты 42, 28, 14, 7 и 2 суток. Интервал polling по умолчанию 7 минут. Для Black Hole сна на сервере настраиваются VibeCode wake schedules в 09:44 и 18:44 по Москве.

## Правило по дизайну

Основной экран левого меню утверждён как финальная визуальная версия. Подробное описание закреплено в `DESIGN_GUIDE.md`.

Без отдельного подтверждения пользователя запрещено менять `public/menu.css`, визуальную композицию `public/index.html`, размеры, цвета, отступы, сетку, порядок блоков и внешний вид элементов. ## Ограничения MVP

- Нет настоящей push-подписки на события счетов на текущем сервере; вместо неё работает polling fallback.
- Если общая раскладка карточки сделки ещё не была явно настроена (`data: null`), приложение не заменяет её вслепую одним своим разделом, чтобы не потерять стандартную карточку.
- Нет полноценного запрета редактирования расчётных полей в карточке для не-администраторов: текущий VibeCode userfields API позволяет выставить `editInList: "N"`, но не даёт отдельный card-level role-based readonly флаг.
- Нет очереди пересчёта.
- Нет отдельного хранилища истории отчётов.
- CSV используется как лёгкий Excel-compatible формат вместо полноценного `.xlsx`.
- Настройки хранятся локально в JSON-файле.

## Возможные улучшения после MVP

- Перенести приложение на новый тестовый портал `https://vibecod1.bitrix24.ru` и новый сервер после отдельного решения о миграции.
- Создать и авторизовать OAuth app key `vibe_app_...`, поднять под ним новый сервер и перенести автоматический пересчёт с polling fallback на push-подписки событий.
- Найти Bitrix24/VibeCode API для полноценного role-based запрета редактирования расчётных полей в карточке сделки.
- Настройка отображаемых колонок отчёта.
- Настоящий `.xlsx` экспорт.
- Ролевая настройка доступа к служебной странице.
- Подготовка структуры манифеста и описания для Marketplace.

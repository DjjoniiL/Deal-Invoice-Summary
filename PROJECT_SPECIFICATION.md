# Спецификация проекта

## Название

Deal Invoice Summary / Расчёт оплаты счетов

## Назначение

Приложение для Bitrix24, которое показывает в карточке сделки финансовую сводку по связанным счетам: сколько выставлено, оплачено, не оплачено и какой остаток по сделке. MVP предназначен для тестового портала VibeCode и дальнейшей подготовки к публикации в Marketplace.

## Целевая среда

- Портал: `https://vibecode01.bitrix24.ru`
- VibeCode server ID: `c576798a-ec5f-4491-b6a2-b28e74fc445f`
- Production URL: `https://app-2657fd62db74.vibecode.bitrix24.tech`
- Runtime: `node20`
- Internal port: `3000`
- Access mode сервера: Black Hole

Отдельная serverless-адаптация для Bitrix24 Marketplace находится в `marketplace/` и предназначена для загрузки zip-архивом без собственной серверной части. Для неё REST-вызовы выполняются из iframe через `BX24.callMethod`, настройки хранятся через `app.option.*` с dev fallback в `localStorage`.

Финальная версия Marketplace-архива: `Калькулятор счетов Marketplace v34.zip`. Runtime/cache marker текущей сборки: `layout-20260817-9`; в видимых местах интерфейса, установочного журнала и диагностических логов используется человекочитаемая версия `Deal Invoice Summary v.34 Marketplace B24`. v34 считается итоговой стабильной serverless-базой для публикации. Массовый расчёт строго уважает выбранную воронку: сделки из других воронок не попадают в очередь и массовый CSV даже при включённом учёте счетов выбранного периода. Массовый CSV содержит колонки `Тип воронки` и `Стадия сделки`. Правая колонка главной страницы адаптирована под узкий iframe, верхняя кнопка обновления перезагружает iframe с cache-busting параметром, модалка статистики открывает стандартный список сделок Bitrix24 по клику на сектор диаграммы с ID сделок, `STAGE_SEMANTIC_ID` и конкретными `STAGE_ID`, автозапуск чата открытой линии останавливает повторные попытки после первого признака открытия, а `Последний запуск` массового расчёта сохраняется в браузере между перезапусками iframe.

### Финальные практики v34

- Автозапуск чата открытой линии реализован только на `settings.html?openChat=1`: сначала API виджета, затем DOM fallback по видимым кнопкам, затем `MutationObserver` для поздней отрисовки. После первого успешного сигнала выставляется `chatOpenDetected`, таймер retry очищается, observer отключается.
- Сектора диаграммы статистики открывают Bitrix24 CRM список по точным ID сделок. `STAGE_SEMANTIC_ID` и `STAGE_ID` передаются как дополнительные фильтры, но бизнес-гарантия перехода держится на `FILTER[ID]`, потому что UI стандартного списка может не показать поле `Группа стадий`.
- Для новых сложных функций Marketplace обязательно добавлять тест в `marketplace/marketplace-runtime.test.js` с описанием блока, сценария и риска.

## Основные сценарии

1. Пользователь открывает приложение из левого меню Bitrix24.
2. Пользователь настраивает сопоставление расчётных полей сделки или создаёт стандартные поля автоматически.
3. Пользователь проверяет расчёт вручную по ID сделки или ссылке на сделку.
4. Backend загружает сделку и связанные счета через VibeCode REST proxy.
5. Backend считает итоговые суммы и возвращает JSON.
6. Приложение записывает итоговые суммы в сопоставленные поля сделки.
7. Совместимый маршрут `/deal-tab` продолжает отображать отчёт в формате вкладки сделки.
8. Пользователь может скачать отчёт в формате CSV, открываемом Excel.
9. Пользователь может открыть карточку счёта из таблицы во внутреннем окне Bitrix24.

## Бизнес-логика

Счета связаны со сделкой через `parentId2 = dealId`.

Сумма счета берётся из `opportunity`. Если значение отсутствует, расчётная функция также умеет принять `amount` или `PRICE`.

Стадии счетов классифицируются по семантике:

- `S` или `SUCCESS` — оплаченный счёт;
- `F` или `FAILURE` — отрицательная стадия;
- suffix `P` — оплаченный счёт;
- suffix `D` — отрицательная стадия;
- остальные стадии — неоплаченный счёт.

По умолчанию отрицательные стадии исключаются из сумм. Их количество попадает в `skippedNegative`. Если настройка `includeNegativeStages` включена, такие счета считаются неоплаченными.

Формулы:

```text
issued = сумма всех учитываемых счетов
paid = сумма оплаченных учитываемых счетов
unpaid = сумма неоплаченных учитываемых счетов
remaining = сумма сделки - paid
```

## Пользовательские поля

Стандартный маппинг:

- `ufCrmInvSumIssued` — выставлено;
- `ufCrmInvSumPaid` — оплачено;
- `ufCrmInvSumUnpaid` — не оплачено;
- `ufCrmInvSumRemaining` — остаток по сделке.

Настройки хранятся в `data/settings.json`.

## API приложения

- `GET /api/health`
  - Возвращает `{ "ok": true }`.
- `GET /api/bootstrap`
  - Возвращает настройки, поля сделки, портал и режим доступа.
- `POST /api/settings`
  - Сохраняет настройки маппинга.
- `POST /api/fields/ensure`
  - Создаёт стандартные поля сделки, если их ещё нет.
- `GET /api/deal-summary?dealId=ID`
  - Возвращает расчёт без записи в сделку.
- `POST /api/recalculate/deal`
  - Принимает `{ "dealId": number }`, считает и записывает итоги в сделку.
- `GET /api/deal-report?dealId=ID`
  - Возвращает CSV-отчёт с BOM и `Content-Disposition: attachment`.
- `POST /api/recalculate/recent`
  - В серверной версии пересчитывает сделки, у которых счета созданы за выбранное окно автопересчёта. В актуальном Marketplace-массовом расчёте окно выбирается как `1 мес`, `3 мес` или `6 мес`, по умолчанию `1 мес`.
- `GET /api/automation/status`
  - Возвращает состояние polling-автопересчёта, интервал, окно свежих счетов, последний запуск и watchlist.
- `POST /api/automation/run`
  - Запускает polling-автопересчёт немедленно.

## Frontend

Основной экран левого меню:

- компактный заголовок с порталом и режимом доступа;
- блок обращения за доработкой приложения;
- сопоставление расчётных полей сделки;
- кнопка создания стандартных полей;
- блок состояния автопересчёта;
- ручная проверка по ID сделки или ссылке на сделку;
- скрытый по умолчанию журнал логирования.
- статус polling-автопересчёта и ручной запуск автопрохода.
- режим расчёта в блоке автопересчёта: в серверной версии `Утром и вечером` использует polling fallback, `Постоянный` зарезервирован для будущих push-событий; в Marketplace-версии дефолтный режим `При открытии сделки`, а серверные режимы ведут на заявку серверной версии без запуска serverless-автоматизации;
- выбор окна пересчёта в блоке автопересчёта, компактная шкала статуса ручного автопрохода и модальное окно скачивания сформированного отчёта.

Маршрут `/deal-tab` сохранён как совместимый экран отчёта:

- верхний компактный заголовок;
- увеличенный круговой график покрытия оплаты;
- четыре числовые карточки;
- блок `Структура счетов` под числовыми карточками;
- таблица счетов с номером, стадией, суммой, датой выставления, сроком оплаты и ответственным;
- контрастная кнопка скачивания отчёта.

Вкладка использует Bitrix24 JS SDK:

```javascript
BX24.openPath('/crm/type/31/details/{invoiceId}/')
```

Если SDK недоступен, используется fallback `window.open`.

## Marketplace serverless: режим при открытии сделки

В Marketplace-версии без сервера автоматический сценарий строится вокруг открытия карточки сделки. Когда пользователь открывает сделку, Bitrix24 загружает iframe приложения во вкладке карточки. Приложение получает ID сделки из `PLACEMENT_OPTIONS`, читает сделку через `crm.deal.get`, получает связанные счета через `crm.item.list` с `entityTypeId=31` и `parentId2 = dealId`, считает суммы и при необходимости обновляет расчётные поля сделки через `crm.deal.update`.

Этот режим называется `При открытии сделки`. Он не является фоновым realtime-режимом: если сделку после изменения счёта никто не открыл, поля сами не обновятся. Но для serverless Marketplace это основной честный автоматический сценарий без backend. Пока карточка открыта, приложение может дополнительно следить за изменением суммы и стадии самой сделки и повторять пересчёт. Перед записью приложение должно сравнивать текущие значения полей с рассчитанными и пропускать обновление, если значения уже совпадают.

Уточнение `layout-20260812-3`: в открытой карточке serverless-версия может реагировать только на изменения, которые уже видны через `crm.deal.get`. Для этого используется polling, проверки при `focus`/`pageshow`/`visibilitychange` и подписка на события placement, если конкретный CRM placement вернёт их через `BX24.placement.getInterface`. Несохранённые изменения во внутренней форме карточки Bitrix24 не являются надёжным serverless-сигналом.

Уточнение `layout-20260812-4`: для Marketplace zip добавлен официальный `PAGE_BACKGROUND_WORKER`. Установщик регистрирует `worker.html` с обязательным `errorHandlerUrl`; worker получает контекст через `BX24.placement.info()` и `PLACEMENT_OPTIONS.URI`, активируется только на URL карточек сделок, проверяет сохранённые `OPPORTUNITY`/`STAGE_ID` каждые 5 секунд, пересчитывает поля через Bitrix24 REST и после записи пробует обновить интерфейс карточки через `BX24.placement.call("reloadData")`, а если команда недоступна из фонового placement, через `BX24.reloadWindow()`.

Уточнение `layout-20260812-5`: worker безопасно разбирает настройки из `app.option.get`/`localStorage` и при ошибке формата использует значения по умолчанию, чтобы мониторинг открытой сделки не падал из-за повреждённой опции.
План доработки serverless Marketplace:

1. Добавить режим `При открытии сделки` в список автопересчёта. Реализовано в `layout-20260812-1`.
2. При открытии карточки сделки пересчитывать связанные счета и обновлять поля только при изменении результата. Реализовано в `layout-20260812-1`.
3. Убрать пункт `Ручной` из списка режимов и выбрать `При открытии сделки` по умолчанию. Реализовано в `layout-20260812-2`.
4. В открытой карточке сделки повторять пересчёт при изменении суммы или стадии сделки. Усилено через `PAGE_BACKGROUND_WORKER` в `layout-20260812-4`.
5. Сохранить ручной пересчёт и массовый пересчёт по окну как действия по кнопке.
6. Режим `При изменении сделки/счёта` в Marketplace работает через `PAGE_BACKGROUND_WORKER` на открытых страницах портала.
7. Beget не использовать для режимов `Постоянный` и `Утром и вечером`.

Backend реализован на нативном HTTP-сервере Node.js без Express и без внешних зависимостей. Это снижает потребление памяти и ускоряет cold start на маленьком сервере.

Ключевые файлы:

- `src/server.js` — HTTP API, static serving, отчёты, интеграция с расчётом.
- `src/vibeClient.js` — клиент VibeCode REST.
- `src/summary.js` — чистая расчётная логика.
- `public/styles.css` — общие стили и экран отчёта.
- `public/menu.css` — финальный компактный дизайн экрана левого меню.
- `DESIGN_GUIDE.md` — утверждённое описание финального дизайна и запрет на изменение визуальной части без отдельного подтверждения.

Фоновый автопересчёт текущей версии реализован как polling fallback, потому что сервер создан под личным `vibe_api_...`, а VibeCode push `event-subscriptions` требуют сервер под OAuth app key `vibe_app_...`. Polling хранит отслеживаемые сделки в `data/watchlist.json`, добавляет сделку в watchlist после ручного пересчёта и пересчитывает watchlist плюс сделки со счетами, созданными за выбранное окно. По умолчанию окно 21 сутки, доступны варианты 42, 28, 14, 7 и 2 суток. Интервал polling по умолчанию 7 минут. Для Black Hole сна на сервере настраиваются VibeCode wake schedules в 09:44 и 18:44 по Москве.

## Ограничения MVP

- Нет настоящей push-подписки на события счетов на текущем сервере; вместо неё работает polling fallback.
- Автоматическое добавление раздела карточки сделки зависит от доступных прав Bitrix24 и раскладок воронок. Marketplace-версия пробует обновить доступные раскладки и при ответе `Card layout is empty` создаёт безопасную дефолтную раскладку с разделом `Расчёт оплаты счетов`; результат фиксируется в журнале `dealCard`.
- Нет полноценного запрета редактирования расчётных полей в карточке для не-администраторов: текущий VibeCode userfields API позволяет выставить `editInList: "N"`, но не даёт отдельный card-level role-based readonly флаг.
- Нет очереди пересчёта.
- Нет отдельного хранилища истории отчётов.
- CSV используется как лёгкий Excel-compatible формат вместо полноценного `.xlsx`.
- Настройки хранятся локально в JSON-файле.
